## Стратегии загрузки и проблема N+1
-   ```Проблема N+1 запросов``` (критическая деградация производительности при итерации по коллекции) - загрузка N родительских записей порождает 1 запрос за родителями + N отдельных запросов за их дочерними объектами
-   ```FetchType.LAZY (Ленивая загрузка)``` (загрузка связанных данных по требованию при первом обращении к геттеру) - возвращает прокси ByteBuddy; бросает `LazyInitializationException`, если сессия уже закрыта
-   ```FetchType.EAGER (Жадная загрузка)``` (немедленная загрузка связанных данных при чтении сущности) - антипаттерн для коллекций; приводит к неконтролируемым скрытым JOIN запросам по всей базе данных
-   ```JOIN FETCH в HQL/JPQL``` (явная жадная загрузка связи в рамках одного запроса) - лучший инструмент точечного решения N+1 под конкретные сценарии интерфейса
-   ```@EntityGraph & @NamedEntityGraph``` (декларативное переопределение стратегии загрузки связей для конкретного метода) - позволяет в `JpaRepository` настроить жадную загрузку связей без изменения сущности
-   ```@BatchSize(size = 25)``` (пакетная загрузка ленивых связей через SQL условие IN) - вместо N запросов выполняет всего `N / size` запросов вида `SELECT ... WHERE parent_id IN (?, ?, ...)`; спасает от N+1 без изменения запросов
-   ```@Fetch(FetchMode.SUBSELECT)``` (загрузка всех дочерних коллекций одним дополнительным подзапросом) - выполняет `SELECT ... WHERE parent_id IN (исходный SELECT родителей)`; сокращает обращения к БД до 2 запросов
-   ```MultipleBagFetchException``` (ошибка одновременной жадной загрузки двух коллекций типа List) - Hibernate запрещает делать `JOIN FETCH` для двух `java.util.List` (Bag) из-за риска декартова произведения; решение: заменить `List` на `Set`
-   ```Hibernate.initialize(proxy)``` (программная инициализация неинициализированного прокси в открытой сессии) - принудительно заставляет Hibernate отправить запрос к БД до того, как объект покинет сервисный слой
