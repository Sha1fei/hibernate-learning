## Транзакции и блокировки
-   ```@Version (Оптимистичная блокировка / Optimistic Locking)``` (защита от потери обновлений при параллельной работе пользователей без блокировки строк) - колонка `version int/long`; при UPDATE проверяется `WHERE id = ? AND version = ?`; при несовпадении бросается `OptimisticLockException`
-   ```OptimisticLockType.DIRTY``` (оптимистичная блокировка без колонки версии) - проверяет только значения реально изменённых колонок в предложении WHERE; подходит для легаси баз данных
-   ```LockModeType.PESSIMISTIC_WRITE (SELECT ... FOR UPDATE)``` (жесткая эксклюзивная блокировка строки на уровне СУБД) - параллельные транзакции ждут завершения текущей; предотвращает параллельные модификации критичных данных (балансы, остатки)
-   ```LockModeType.PESSIMISTIC_READ (SELECT ... FOR SHARE)``` (разделяемая блокировка для чтения) - запрещает другим транзакциям изменять строку, но разрешает её читать
-   ```jakarta.persistence.lock.timeout (Таймаут ожидания пессимистичной блокировки)``` (защита от бесконечного зависания потоков) - преобразуется в `NOWAIT` или `SKIP LOCKED` в PostgreSQL/Oracle (`PessimisticLockException`)
-   ```Pessimistic Deadlock (Взаимная блокировка)``` (ситуация перекрёстного ожидания блокировок между транзакциями) - решение: всегда обновлять связанные строки в одинаковом строгом порядке (например, сортируя по ID)
-   ```Уровни изоляции транзакций (Isolation Levels)``` (баланс между параллелизмом и аномалиями данных) - `READ_COMMITTED` (дефолт в PG/Oracle, исключает Dirty Read); `REPEATABLE_READ` (исключает Non-Repeatable Read); `SERIALIZABLE` (полная строгость)
-   ```@Lock на методах Spring Data репозитория``` (декларативное наложение пессимистичной блокировки на сгенерированный запрос) - `@Lock(LockModeType.PESSIMISTIC_WRITE)` над `Optional<Account> findById(Long id)`
